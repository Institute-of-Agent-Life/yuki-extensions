# 跨倉庫依賴與驗收矩陣｜v3.2 核心文檔補核版

**本表是施工順序、跨倉發布與驗收映射的權威文件。** 行為定義見[總書 K00–K15](Yuki-Rust重寫總任務書-v3.2.md)，逐提交詳情見[核心卡](核心倉庫-提交級任務書.md)與[擴展卡](擴展倉庫-提交級任務書.md)。以下 tag、腳本和產物都尚未建立。執行下列工作卡不代表獲准發布、打付費端點或改動生產。

## 1　第一批與不可原子合併的交接

**推薦首批：CORE-001 與 EXT-001 可同時開始；接 CORE-002，再並行 CORE-003、004、049、EXT-007。CORE-005 可在 CORE-001 後另外開工。** 先用固定舊程式取得 wire/行為，不能把新版自行生成的正例當舊真值。三個初始參考產物是「送達後的下一正常 Main 請求」、「App 補原 QQ Work 的事件/郵件/回執」及「分段發送僅部分確認」。

**一種可執行的 PR/發版方式。** 先合 producer 的向後相容變更，由該合併 SHA 建置並發布不可變預發產物；consumer 獨立 PR 將 SHA/digest 寫入自己的 lock，從公開包建置並交回結果。producer 的 PR 用已發舊 consumer＋自己生成的候選包測，不以尚未合併的新 consumer 為通過條件。跨倉試驗可使用附 SHA/雜湊的 CI 候選包，但不得把短命 CI URL 作已合併消費者的永久 pin。正式來源用兩倉各自的 Releases/package registry/OCI，不建第三個 schema 或部署倉。

**B0 的穩定面。** `initialize`、版本與必要能力協商、關閉/重握；綁原 namespace 的 `gateway.inbound` 與接納後 ACK、無 I/O 發送計畫及逐片 dispatch/回執；受權 `tool.call` 及 result/error、原鍵、作用域與撤權失敗。以兩真包走一次 TG 入站→主模型要求取網頁→工具結果→TG 部分發送，假上游可控；另驗重投不重送。**隱私驗收有兩個可預先判斷的分支。** 兩個真包各交安裝設定、正常運行及 kill 後的資料持有清冊。發現持久的來源私料（包括尚待交付的原附件）時，必須在該真持有者上驗原鍵 `forget.request/ack`、清除後重啟及不復活；任一失敗即不准發該組 B0。兩包都沒有持久的來源私料時，對臨時資料仍驗撤權、關閉後不可讀及遲到發表被拒，不造假表；1.0 不列「持久 owner 清除 RPC 已穩定」，任何要求該能力的插件不能用這個 stable 組取得新權限。第一個真持有者（例如 EXT-032 的收藏原件或 EXT-037 的診斷私庫）通過後再依 CORE-053 發 additive minor。既有實例若還有持料 owner，一律保持原有可清理 reader／原組，不能以這個新裝基底略過未交清除義務。若 TG 啟動依賴額外方法，同樣逐項見證才列入。可選未驗者不外宣。1.0 是公共介面承諾，不等於全資料域 forget 已驗、所有能力可部署或真平台已上線。

**取代順號 alpha 列車。** 候選包按合併 SHA/IDL hash/feature manifest 發布，預發版號例如 Rust `X.Y.Z-rc.N`、Python `X.Y.ZrcN`，N 是發布方唯一配號，不是功能順序。真消費者用一個實際包含所需方法的 host digest，不能把兩個分支各自的綠燈相加。stable SDK 僅匯出已證的方法；發版器以原始 schema 投影並核 digest，不複製第二份手寫 IDL。一般安裝不默認協商候選面。

**每個 minor 的競爭與回退。** `parent_stable_digest + candidate_SHA + surface_diff + consumer_digest + 方法見證` → 下一個 `1.n.0`。新 stable 是上一版全部穩定面加本次已驗增量，不預配各域版號。兩個域同時完成，後發者 rebase 至最新已發 stable、重建同一套件、重跑舊消費者與本次正反例；舊版不覆寫。合併新的 core 功能不自動晉級。固定的 CORE-053 是發版工具提交；往後每次是可重複、具名且有獨立 manifest 的發布操作。場景失敗、漏證、舊宿主錯放未授權效果，均不移動正式指標。binary/SDK、插件、Connector、setup 與 OCI 各有獨立版本及 digest；不覆寫舊 wheel 0.4.3，不靠推 main 更新另一倉。

**相容規則。** 加可選欄位、不改缺省語義且舊方可忽略＝minor；修實作而不改已接受輸入/效果語義＝patch。刪/改欄位、舊值另解、要求新權限/新副作用、錯將 unknown 改成功均不得偽裝 additive。新增特權預設拒，不能靠默認啟用「升級」。破壞改動先發布雙讀／雙協商的 host，維持舊寫入格式或明示 min_reader；consumer 遷移與回讀測完，才經獨立下一版撤舊。跨 major 保上一個仍被宣告支持的讀者；原效果/已付資料的 reader 不隨 writer 升級刪。SQL schema、Plugin wire、個人 Client revision、Connector wire、原生 ACP 與 VM 快照 ABI 各自獨立。

| CI 格（H=宿主，X=插件） | 執行處／動作 | 期待；不支持時怎麼判 |
|---|---|---|
| H_last + X_last | 兩倉 release smoke 從原 BOM 下載，不用 main | 正控，必綠且舊組不被原地更新 |
| H_candidate + X_last | core PR 用前一已發布實物、原資料卷 | 保向後相容；不能因缺新功能把原插件執行變未知；測舊資料讀取 |
| H_last + X_candidate | extensions PR 用公開 host digest | 在宣告範圍內真實成功；要求超出該 H 的能力時局部拒絕、原組仍可用。拒絕不得列為支持格的通過 |

| 零插件／有插件失敗／不同架構 | core/擴展各負責自有分發；Desktop 另測 OS runtime | Linux 核心最小＋全棧 gVisor/VM；Mac/Windows 驗可分發 binary/Connector/桌面組；不可用組件標不支持。真機缺額標待採，不用 skip 宣稱已驗 |

第一次沒有 last-stable 時使用上一個已發布的固定基礎候選/公開舊 consumer 的適用路徑，單列 bootstrap，不造歷史正式版本。後續 schema 生成器、SDK、OpenAPI、API9 舊 reader 只認 core 發布者原件；consumer 可以保有生成/驗證副本但 CI 比 hash 且禁止手改。Connector 的外部依賴是上游 wire4/SDK 原事實，與新的插件 stdio 無關。

## 3　跨系統 E2E 劇本（驗證組，不是有待上線的背景任務）

**讀法。** 每卡「先決」是排程的直接邊。若 C 同時讀 A 與 B，而 B 已必須取得 A，C 的先決只列 B；原 A 的報告和 pin 在「沿途已取得的輸入」列明。這只刪重複排隊，不能換用別版。卡尾「直接交給」反查先決。共同合同、階段、同倉 manifest、或提交號並不是額外等待條件。
